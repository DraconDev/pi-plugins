# pi-chrome-always audit — 2026-11-24

Re-runnable: `extensions/pi-chrome-always/scripts/audit.sh` (also `npm run audit`).
Read-only: it starts no Chrome, loads no extension, changes no file, and sends only
`/status` plus `data.extensions.list` (both read-only). Exit 1 = findings, 2 = a
check could not run, 0 = clean.

## What "the browser we made" is

`pi-chrome-always` is our fork of the Pi Chrome connector: a Chrome extension plus an
always-on loopback bridge (127.0.0.1:17318) that lets any local Pi session drive the
operator's real, signed-in Chrome profile. It exists to add two things upstream
pi-chrome does not have: browser-data permissions (cookies, history, bookmarks,
downloads) exposed through `chrome_always_data`, and an always-on daemon that survives
the Pi session.

Because it holds those permissions against a signed-in profile, "is it the thing that is
actually running, and can anything else reach it" are the two questions worth asking
before it is trusted.

## Findings (live, 2026-11-24)

### 1. The extension actually polling is upstream's, not our fork — HIGH

Chrome derives an unpacked extension's id from its absolute path, so our fork loaded
from `~/.local/share/pi-chrome-always/browser-extension` is a different extension from
the one in `~/.pi/agent/npm/node_modules/pi-chrome/...`. Both poll the same `/next`
queue and whichever polls first wins each command.

Observed: `/status` reports `clientName = "Pi Chrome Connector bnpmpdbgdgmbkeeoefmieafcdkacbllb"`,
and that id is the sha256-derived id of the **upstream npm package** path. The fork's two
ids (`knglfc…` installed copy, `kdmffca…` repo copy) are neither.

Consequence, confirmed by probing the live bridge:
`cdp.targets` → `{"ok":true,…}` (upstream-only action) and
`data.extensions.list` → `{"ok":false,"error":"Unknown action: data.extensions.list"}`
(fork-only action). So the browser-data capability this fork was built for is
unreachable today, while `scripts/doctor.sh` reports a healthy bridge it never served.

### 2. Our fork dropped `cdp.call` and `cdp.targets` — HIGH (latent)

The fork was cut from an older upstream; upstream 0.15.57 has since added the raw-CDP
passthrough. The fork's service worker implements 29 actions, upstream implements 29, but
the sets differ: the fork lacks `cdp.call`/`cdp.targets` and adds
`automation.windowMove`/`automation.windowState`.

This is latent only because upstream's extension is the one loaded. If anyone follows
our own README ("Load unpacked → ~/.local/share/pi-chrome-always/browser-extension")
they get a worker where **`cdp.call` does not exist** — and
`/home/dracon/Dev/dracon-strategy/ai-auto-writer/scripts/_bridge_cdp.py` calls exactly
that. Every Google Play Books script in the book campaign depends on it:
`_google_drop_upload.py` (`DOM.setFileInputFiles`), `google_ship_pen.py`,
`google_attach_series.py`, `google_cover_state.py`, `google_read_catalogue.py`,
`google_wave_contract_proof.py` and ~20 more import `cdp`/`evaluate` from it. Loading
our fork in place of upstream silently breaks the campaign's Google leg with
"Unknown action: cdp.call".

Upstream also added background-mode focus gating (`CDP_FOCUS_METHODS`,
`foregroundRequested`, `cdpCallTimeoutMs`) that the fork does not have: the fork's
`bringToFront` focuses the tab unconditionally, so the raw-CDP escape hatch could
defeat the background-mode policy upstream now enforces.

### 3. The systemd unit never enables the token — HIGH (latent)

`~/.config/systemd/user/pi-chrome-always.service` sets `PI_CHROME_BRIDGE_HOST` and
`PI_CHROME_BRIDGE_PORT` but not `PI_CHROME_ALWAYS_TOKEN`. The daemon enforces the token
only when that env var is set; a token file alone never enforces (the daemon's own
comment says so). So with our extension loaded, `/command` accepts a request from **any
local process** — and the actions it can then reach include `data.cookies.list`,
`data.history.search` and `data.downloads.list`, i.e. the operator's session cookies
and browsing history. The upstream in-Pi server has the same loopback-trust model but
does not implement the browser-data actions, so today this exposure is fork-only.

### 4. The fork declares two permissions its code never uses — MEDIUM

`browser-extension/manifest.json` declares `notifications` and `desktopCapture`;
neither `chrome.notifications.*` nor `chrome.desktopCapture.*` appears anywhere in the
fork's service worker, injected script or offscreen document. Upstream declares neither.
They are pure extra reach on a signed-in profile.

### 5. The always-on daemon is not running — MEDIUM

`systemctl --user is-active pi-chrome-always` → `inactive` (unit file present and
installed, service last ran 2026-11-13). The bridge currently answering on 17318 is the
in-Pi upstream server owned by this Pi session, so it dies with the session. The
"always-on" property the fork exists for does not hold right now.

## Resolutions (2026-11-24)

| # | Finding | Resolution |
|---|---|---|
| 1 | Wrong worker polling | The fork's manifest now pins an extension id via `key` (`kmjcfjgefmkhmickoakebpmlhikabega`), so it is the same extension from any install path and is identifiable in `chrome://extensions` and in `/status`. Its worker announces `Pi Chrome Always <id>` (upstream says `Pi Chrome Connector <id>`), so "which worker is serving" is answerable from `/status` alone. The fork holds the `management` permission and **disables the rival upstream connector on startup**, so exactly one worker answers the queue. The daemon also reports every extension that has polled (`pollingClients`), and `doctor.sh`/`audit.sh` fail loudly when the serving worker is not the fork. |
| 2 | Dropped `cdp.call`/`cdp.targets` | The fork's worker **and** its Pi-side `index.ts` were rebased onto upstream 0.15.57, re-applying only the fork's own additions (browser-data actions, owned-window diagnostics, offscreen keepalive, evaluate output cap, bridge token, indefinite auto-auth, daemon assurance, cold-start safety net, `chrome_always_data`). The fork is now a strict superset: 42 worker actions vs upstream's 34, and 24 Pi tools vs upstream's 23, with **nothing upstream implements missing**. Upstream's background-mode focus gating came with it. `scripts/test-worker-contract.mjs` pins this. |
| 3 | Token never enforced | The daemon now reads the token file (`~/.local/share/pi-chrome-always/token`, mode 600) instead of requiring an env var, and **always** requires it for the `data.*` browser-data actions — the ones that reach the operator's cookies and history. Ordinary actions keep upstream's loopback-trust model so an upstream pi-chrome client and the book campaign's `scripts/_bridge_cdp.py` keep working. `PI_CHROME_ALWAYS_REQUIRE_TOKEN=1` opts into demanding the token for every action. The Pi-side bridge applies the same gate. |
| 4 | Unused permissions | `notifications` and `desktopCapture` are gone. `offscreen` was added because the fork's offscreen keepalive document actually uses it — without it the keepalive silently did nothing. |
| 5 | Daemon not running | The unit is now `enabled` and `active` (`Restart=always`), and it waits for the port rather than failing when a Pi session already owns it. |

## Remaining operator step

Loading the fork's extension into Chrome still needs one click in
`chrome://extensions` → *Load unpacked* → `~/.local/share/pi-chrome-always/browser-extension`.
Chrome blocks extension automation on `chrome://` pages, and this Chrome is a native
Wayland client (no X11 window), so the repo's xdotool picker helper cannot reach the
native file dialog. Everything after that click is automatic: the fork disables the
rival connector, and `doctor.sh`/`audit.sh` prove which worker is serving.

Until then `audit.sh` correctly reports finding 1 as still open — the fork's
browser-data capability is unreachable while upstream's worker is the one serving.
